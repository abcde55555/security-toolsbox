# EN18031 合规测试平台 · 产品需求规格说明书（PRD）

> **文档版本**：v1.0
> **产出日期**：2026-08-14
> **适用读者**：产品经理、前后端开发工程师、合规模组开发工程师、测试工程师
> **读完后你能做的事**：判断自己开发的功能是否属于 MVP 交付范围、是否符合三层架构、是否满足 EN18031 审计场景的权限与交付物要求。

## 1. 产品定位与目标

1. 产品定位。本产品面向需要依据 EN 18031（或同系列 IoT 安全合规标准）开展设备合规测试的测试团队与审计机构，提供「工具统一管理 — 测试流程模板化编排 — 项目级执行 — 合规报告自动产出」的一站式工作台。核心价值是，解决当前合规测试依赖人工拼命令、手动写报告的问题，把所有操作可追溯、可复用、可批量重跑。

2. 核心目标。1 个项目、1 个 EN18031 模板、10+ 个检测工具，从「创建项目」到「导出合规报告」，不需要测试工程师手动输入任何一条命令或手写任何一段报告正文，平台按编排顺序自动跑完所有启用步骤、按 EN18031 条款自动汇总判定结果，最终产出可归档的 PDF/Excel 报告。

3. 非目标。本期不做：SaaS 多租户商业运营、AI 漏洞语义分析、漏洞 PoC 利用验证、渗透测试人工步骤辅助。本期聚焦「合规测试」而非「全栈渗透」。

## 2. 角色与权限（预留设计，首期最小落地）

1. 角色清单定义三种基础角色，接口与数据层全部预留，首期 UI 不做用户管理页面，当前默认以「系统管理员」单角色运行即可。系统管理员 Admin，权限范围全部，含注册/修改/删除全局工具库、管理模板、创建/删除项目、运行工具、导出报告、管理预留的用户与角色；模板管理员 Template Manager，不能改全局工具库，其余与 Admin 相同；审计员 Auditor，只能打开已有项目、跑编排、看报告、导出报告，不能改模板不能改工具不能创建删除项目。

2. 首期最小实现。首期登录鉴权可选，接口层必须保留 `Authorization` 头解析和一个 `req.user.role` 的角色判断钩子，所有写操作接口必须在 Controller 层有 `requireRole('admin')` 类的占位校验函数，函数内容可以先直接放行，但结构不能少，避免后期补时每个接口重新改一遍。

3. 审计可追溯性。所有写操作（工具注册、模板变更、项目创建、命令执行）必须留下操作人ID和操作时间戳，日志的「只追加不可清除」特性是合规硬性要求，任何版本都不能取消。

## 3. 三层架构需求（继承 v6 原型的全局工具库架构）

1. 第一层：全局工具库。所有工具在此统一注册一次，模板和项目都是引用而不是拥有，解决工具跨模板丢失的问题。分类维度支持分类 Category + 标签 Tag 双维度，首期分类固定、标签先留数据结构；工具来源分内置模组和自定义工具两类；交互模式分命令行型和表单交互型两类；每条工具注册记录包含路径、版本、引用计数、健康状态灯、能力标签列表。

2. 第二层：模板管理。模板是「引用的工具集合 + 执行编排流程 + 启用命令集合」的可复用单元。必须支持克隆；必须支持对引用工具的版本做跟随或锁定两种模式，锁定模式下全局升级不影响已引用的模板，跟随模式受影响且需给出红色升级提示；必须支持编排流程，即定义第几步跑什么工具、用什么默认参数、是否依赖前置步骤的产物；必须支持项目级变量占位符如目标IP、网段、端口范围，使模板一次配好、多项目复用。

3. 第三层：项目管理。项目 = 绑定的模板 + 目标变量赋值 + 执行历史 + 产出的报告。必须支持一键启动整套模板编排流程，进度可感知、可中止；必须支持单独切换到单工具模式手动执行；执行结果必须同时写入终端实时输出和审计日志；所有执行结果必须汇总成项目级的合规报告页，映射到 EN18031 具体条款，并支持导出 PDF/Excel。

## 4. MVP 交付范围 P0（不满足则平台不可投入实际合规审计使用）

1. 内置模组 SDK 契约的首个稳定版本，明确 formFields JSON-Schema、字段校验规则、执行进度回调签名、标准化执行结果格式（含 clauseId 级别的判定输出）。无此契约则每开发一个合规模组就要重接一遍接口，10 个模组后工程代码会腐烂。

2. EN18031 条款映射机制。条款必须是结构化数据，含条款编号、章节、标题、合规等级阈值、测试方法描述；每个工具的每条命令或每个表单交互型模组的每个判定输出项必须能映射到 1 个或多个条款编号；项目报告页必须按条款分组显示证据和判定。

3. 模板编排能力。模板必须支持步骤化编排：多步骤有序执行、每步绑定具体工具及默认参数、支持步骤依赖声明、支持单步失败策略继续或终止；首期可先用列表式UI，不强求拖拽。

4. 项目级目标变量面板。在项目详情页可维护「目标IP」「目标网段」「合规等级」等项目变量，模板中所有占位符统一从这里读取；同时支持「多个目标」的批量执行，首期至少支持"目标列表顺序执行"。

5. 工具版本锁定与兼容性提示。模板引用工具时必须带 lockVersion 字段；工具升级后所有引用它的跟随模式模板必须有红色角标提示"引用的X工具已升级，请确认兼容性"。

6. 项目报告页。项目页必须新增「报告」Tab，内容包含合规定级 L1/L2/L3、PASS/FAIL 条款统计仪表板、每条条款的证据追溯（哪次执行、什么命令、什么输出、判定理由）、一键导出 PDF 和 Excel 归档包。

7. 数据持久化与执行引擎接口。所有三层数据必须有明确的持久化模型；执行引擎必须有标准接口抽象：命令执行型走 PTY/子进程，表单交互型模组走 SDK 调用，结果统一按格式推送。

## 5. 首批迭代关键能力 P1

1. 长时间任务的进度显示与中断控制。nmap 全端口扫描、固件解包分析等长任务必须支持进度百分比展示、ETA 估算、暂停继续、强制终止。

2. 工具健康检查。工具库卡片、模板引用区、项目切换工具三个位置都必须展示工具健康状态灯：绿色表示路径验证通过且版本匹配，黄色表示版本号不匹配但可尝试运行，红色表示找不到或权限不足；点击健康灯可触发一次实际运行 `--version` 的校验。

3. 模板克隆与继承。支持一键复制已存在模板为新模板；保留父子关系，父模板的引用工具变更后子模板可以看到提示并选择合并或忽略。

4. 错误状态的语义化处理。新增超时、工具崩溃、EDR 拦截、权限不足、部分成功 5 类错误状态；不同状态下报告页的判定结果不同（如超时=未知，部分成功=按已成功结果判定并标注不完整）。

5. 自定义工具开放表单交互模式。不再将表单交互能力限制为内置模组专属，自定义工具注册时同样可以提供 formFields schema，满足企业客户将自家脚本封装为表单一键执行的需求。

6. 日志检索与筛选。审计日志追加列表支持关键词搜索、按成功/失败/执行中/已拦截等状态筛选、按工具名筛选、按时间范围筛选；注意"筛选"不等于"删除"，原始日志实体不可清除、不可编辑。

## 6. 体验与远期拓展 P2

1. 响应式布局与窄屏适配。至少在 1024 宽度断点下提供侧栏收起、工具详情可折叠为 Tab 的能力，保证 13 寸笔记本屏幕可用。

2. 分类+标签双维度筛选。分类保持导航一级结构，标签支持多值多选、可由 Admin 自定义。

3. 工具版本变更记录与回滚。工具、模板、项目配置的每次修改都有变更记录，支持一键回滚到上一个版本。

4. Workspace/多团队隔离。在单部署实例下区分不同产品线团队的工作空间，模板工具项目互不干扰。

5. 第三方模组沙箱市场。远期开放第三方合规模组上传，但必须有沙箱和权限审计机制。

## 7. 交付里程碑（建议顺序）

1. Milestone 1 — 架构地基。交付内容：数据模型落地、执行引擎接口抽象、内置模组 SDK v1、条款映射机制；验证标准：可以用 SDK 写一个 port-check 模组并在真实环境下跑出一条条款判定。

2. Milestone 2 — MVP 闭环。交付内容：P0 范围全部、持久化、权限钩子、模板编排、报告页与导出；验证标准：拿一个 IoT 摄像头产品，按模板从头跑到尾，一键导出完整 EN18031 报告。

3. Milestone 3 — 体验与效率。交付内容：P1 范围全部、长任务进度、健康检查、日志筛选、模板克隆；验证标准：实际测试团队跑一周无阻塞性反馈。

4. Milestone 4 — 扩展能力。交付内容：P2 范围筛选、版本回滚、多 Workspace、响应式；验证标准：多产品线团队接入、笔记本窄屏可用。
